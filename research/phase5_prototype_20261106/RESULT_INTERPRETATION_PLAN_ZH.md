# Phase5-A 结果判读清单

2026-11-06。已读 PLAN_AND_FORMULAS_ZH.md 与 QUALITY_PROTOCOL_V1.json；尚未读取本轮真实模型输出。模型已启动，因此本页不冒称新的 prelaunch 预注册，只固定后续分析边界；没有启动新实验或改源码。

**先回答质量问题，再讨论效率。** 本轮是两个程序的六个 E/C/W 状态、共享精确根 G 的四种一次提示，不是六道独立自然题、完整 controller 或新训练方法。结果到达后再写 RESULTS_CRITIQUE_ZH.md，不能预填胜负。

## 1. 首先确认结果是否回答了质量问题

先核源/adapter/数据/模型/parser/token 渲染冻结、实际设备/版本、complete 标志、原文与成本账。按协议分开呈现：

- 计划 6 主状态、开始多少、完成多少四臂配对；2P/4PR 六个能力控制是否完成。
- frozen-parser numeric_correct 与 EOS-and-correct；EOS、512-cap、未解析、错误分别列。
- 完整四臂同分母；固定顺序尾部未跑不能算“无错误”，也不能拿未完成单臂与已完成配对拼优势。
- 只有所有方法大多自然 EOS，宽松保护顶没有重新成为主要约束，才能较好回答本轮“正常完成谁更可靠”。cap 多时应明确质量估计仍受保护策略限制。

不做动态 parser 早停，答案出现后仍继续至 EOS；如果多余续写导致最终解析失败，保留失败。可解释原文中是否曾出现正确目标值，但不据此改冻结主分数。

若只有 E/C 配对完成、W 未跑，就不能评价错误修订稳健性；若只有能力控制完成，就只能报告这些控制，没有主方法比较。

## 2. 四种方法的关键比较

共同输入含原始定义/图、旧 B/R 和 root-only G；旧 y/z 均 UNVERIFIED。主要对照是：

1. **G+Direct vs G+Compact/Stepwise：** 给定共同信息，显式表达/分解是否提高最终交付。
2. **VersionFrame vs 最强 Compact/Stepwise：** 版本/前沿表示是否超越充分而精简的普通解法。
3. **E 与 C/W 分开：** 处理真修订的收益是否伴随无变化/错误修订损害。不能只挑 E 赢家。

不要只拿 VersionFrame 对 Direct 的差当作版本机制增量：差异也可能来自是否要求推导、更清楚的目标及更长提示。

## 3. 不同可能结果应怎样说

| 实际结果 | 支持什么 | 不支持什么/下一门槛 |
|---|---|---|
| 所有强方法都自然结束且全对 | 共同信息下这两个程序可稳定完成；暂无质量差 | 不认证 VersionFrame 更优。质量相同先保留最简单可靠方案，再看真实成本，不急着造新算法 |
| Compact/Stepwise 与 Frame 同样好，均高于 Direct | 显式计算或分解有用 | 版本表示未获独立增量；采用较简洁方法，后续新程序检验，不回到紧64制造差距 |
| Frame 高于最强强基线，且 C/W 无新增损害 | 当前两程序、固定 G/模板下的提示组织有增量迹象 | 不等于完整 controller、内部阶段指针或自然泛化；先用独立程序/变量名/规则组合确认 |
| Frame 更差或只有更长输出 | 当前静态工作帧没有质量价值，可能冗余/冲突/干扰 | 不等于所有版本控制理论无效；本原型不得升格，先检查具体错绑与提示歧义，不能自动加训练救场 |
| E 改善但 C/W 受损 | 有条件修订收益，同时有伤害 | 不可宣称稳健/安全；核查模型是否忽略 G、读错父版本、误用旧值，保留反例 |
| EOS 分数看似提高但主要是其他方法 cap | 结束/长度策略差异可能是关键 | 不能主要归因为推理更强；宽松质量轮尚未充分摆脱截断，另行说明边界 |
| 都大量 unparsed/拒答/循环 | 交付契约或提示接口存在问题 | 不把它解释成数学能力全错；停止性能叙事，先修接口或另定读出协议，不改本轮分数 |

不能只看聚合准确率：两个程序的正确 z 在每个程序三组中重复，六状态是相关变体。不给总体自然准确率、显著性、pass@1 benchmark 或 90%/50% 预测。

## 4. 能力控制的解释

P-only 不含旧记录/修订/G；P+R 不含旧 B/G，其中错误 R 按原文保留，不假定可信。它们使用各自冻结的简短可计算指令，是能力/干扰 sanity check，不是相同输入信息的方法排名。

- P-only 正确、P+R 错误：在该提示下错误修订可干扰；不唯一定位 KV/版本/指针。
- P-only 或 P+R 不会做、共享 G 方法会做：可能有根算术工具和显式信息的帮助；不能把全部收益归给工作帧。
- P-only/P+R 都对、主方法某臂错：旧 B、G/图/说明的序列组织或方法指令可能造成额外干扰；这可支持简化上下文，不自动证明必须删除 KV。
- 六个控制都对：只能说明这两个程序在这些冻结控制里可解，不是所有读出或自然任务能力 100%。

能力控制按精确 P/(P,R) 去重；E/C 共享同一个 PR 不是两次独立成功。主方法请求没有跨 job KV 或权重更新，不应构造“后面的例子学会了前面答案”的故事。

## 5. G 与版本算法的结论边界

G 从合成原题只核 x/r 根，依赖结构也来自受限、已知语法。它不检验模型输出的 y/z，既不保证旧 z 有效，也不给模型最终答案颁证。G 在合成域的确定动作不能当作自然语言门控误报/漏报的评估。

本次 VersionFrame 是一次可见表示：没有逐步 proposal/check/commit、没有动态更新证书、没有多轮停止/回滚控制。即使全对，只能说“在共享根证据条件下提示出了正确答案”，不能说“验收协议成功率全对”。未来完整 controller 的门槛仍是检查器、状态与规则版本、缺边/unknown、拒绝分支恢复及真实成本。

Exact AST 可以解完整个小程序，这是受控域的合法参考能力，不应把这种 oracle 权限偷换成 LLM 新能力。本轮刻意只给根算术，比较的是其余组合求解的组织方式。

## 6. 成本作为次级结果，不能替代质量

先看同轮质量，再看原始 prompt token、生成 token、G/bookkeeping、编译/tokenize、prefill/decode 和请求 wall。工作帧更长时可能省输出但增加 prefill；每请求 G 已真实重算，且 shared preparation/load 在实验总 wall 中，分项不重复相加。

对等质量方案，可以据真实请求成本/稳定性选择较简单者；若质量不同，明确列 Pareto 权衡，不用“少 token”替代答对。仍不声称已完成同预算前沿曲线，本轮也不能与旧 64-token P0.5 跨协议算方法提升。

## 7. 读到结果后的建议顺序

1. 完成原始文件、冻结绑定、分母和成本验收。
2. 展示六状态×四臂原文与 E/C/W、EOS/cap、parser 结果；列 paired gain/loss。
3. 优先决定哪一个简单原型值得保留，而不是先决定一个必须胜出的研究名。
4. 只有非截断、非共同 oracle、非纯格式可解释的增量，才支持一次独立程序确认；没有增量就停止复杂工作帧的升级。
5. 需要完整 controller 时另立实现与验收任务，不在本结果中补写“已实现”。自然 P1 标签、独立数据、多模型/训练/预算曲线均仍后置，不由这轮自动授权。
