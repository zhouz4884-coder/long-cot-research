# 新建议审查与下一轮主算法设计

2026-11-06。已完整读取新附件，并重新核对 P0.5 的逐例 JSON、80 个原文、条件 Y probe、token ID、冻结协议及独立数值审计。本文件只做设计和本地只读核查；没有运行 GPU、远程任务或 Git 写入。附件属于第三方建议，其实验安排没有自动执行。

**我支持灵活转向“预算内、版本一致的局部重推”，把 KV 操作降为可选实现。下一轮的判断标准应是：在相同信息、工具权限和完整成本下，是否优于紧凑重推和简单门控路由。** 新建议提供了可测试的模块，但“90%+ 准确率、节省 50% token、C/W 必然满分”都尚无实验支持，不能写入仓库的结果区或方法保证。

## 1. 原数据支持什么

本轮冻结评分的主结果仍应原样保留，不能用事后解释覆盖：

| 臂 | E（8） | C（4） | W（4） | 合计 |
|---|---:|---:|---:|---:|
| FullDirect | 0 | 4 | 4 | 8/16 |
| FullOneLine | 5 | 3 | 3 | 11/16 |
| WholeEarlyDirect | 0 | 0 | 0 | 0/16 |
| WholeEarlyOneLine | 6 | 3 | 3 | 12/16 |
| WholeLateOneLine | 4 | 2 | 2 | 8/16 |

这是 16 个人工注入状态上的冻结提取分数，非自然任务总体准确率。辅助诊断只完成前 8 例，3 个预声明控制状态通过完整控制，其余状态不能标为完整控制 PASS。新建议不能把这些边界改写成“机制已经完全清楚”。

### 1.1 “FullOneLine 丢掉五题，其实数学 100% 全对”需要拆开

五题确实都用完 64 个 token，但原文分为两类：

| 案例 | 实际末尾 | 能确认的事实 |
|---|---|---|
| E01 | 已写 `z=35-5=30`，随后停在“最终答案” | 正确 z 已出现，正式提交/提取未完成 |
| E07 | 已写 `z=48-11=37`，停在“最终答案：” | 正确 z 已出现，提交未完成 |
| C04 | 已写 `z=29-9=20`，停在“最终答案” | 正确 z 已出现，提交未完成 |
| E08 | 停在 `81+1=` | 最终数 82 尚未输出，不能说已完成求值 |
| W04 | 停在 `4*20-1=80` | 当前式子/终值是错的，正确值为 79；不能把未来可能补上减 1 当作已发生 |

因此可以说“发现明显提交预算瓶颈，至少三例已得到正确 z 但未按协议提交”。不能说五例全部算对，或预言补一两个 token 后必然正确。下一轮可以研究提交调度，但旧主分数仍为 11/16。

### 1.2 数值落地值得测试，但不是已证明的必要条件

C03 的 FullOneLine 也只列出 `x=35//5；y=x+8；z=2*y`，没有展开中间整数，却正确输出 30；WholeEarly/WholeLate 同样形式分别给出错误 56/76。这个直接反例说明“没写中间数就一定算错”不成立。

“显式代入并产生具体值”仍可能减少变量绑定错误，值得作为提示/执行约束测试。要区分三件事：写出了整数、这个整数满足规则、它引用的是当前父版本。仅语法上出现 `=整数` 不能认证数值正确或版本一致。

### 1.3 四个条件 probe 的排序成立，100% 预测不成立

FullOneLine 的 E01/E02/E03/E04 独立 `y =` 条件下，所评分的少数完整数字串中，至少一个 old_y/root_misbind 的 logP 高于 trusted_y；该数字事实可复核。但它不是“模型被问 y 时 100% 会选错”的行为测量：

- 评分对象是 `整数+换行` 的完整条件序列，不是自由生成的唯一候选集；模型还可能先续写符号、空格、代入式等。
- Y 前缀不含真实生成的一行推导，不能拿它当模型生成完过程后的自然信念。
- E03 的 trusted_y 首 token logP 高于 old_y，完整数字串排名却相反，说明排名还受后续 token/终止形式影响。
- 只有四个 E 状态的这个探针已完成，既不支持自然任务总体规律，也不能唯一识别“必须规则+父值”的内部机制。

工作帧同时显示规则与当前父值是合理候选设计；应由同权限消融检验增量，而不是由 probe 排序直接当作真值证明。

## 2. G 能否让 C/W 零重推，取决于认证了什么

在这些人工 fixtures 中，C/W 的旧 B 被生成器构造成全对。更关键的是：**FullDirect 在 C/W 已是 8/8，仅生成 25 token；FullOneLine 是 6/8、395 token。** 因此 G 旁路若做到 8/8，只能恢复到现有廉价 Direct 已达到的水平，不能作为相对所有强基线的新增准确率收益。

可成立的旁路条件是：修订不改变有效状态，或新修订已被可靠拒绝；并且旧最终值的依赖、数值与版本证书仍有效。这时可以复用已认证的 z，不必让 LLM 再求值。

不能仅凭“旧 x 正确”认证“旧 z 正确”。自然轨迹可能 x 正确但 y/z 原先算错；也可能规则、另一个父变量或数据源已经改变。G 只查 x 的局部约束，不自动给整条旧链颁证。未知时要保留 unknown/弃权或使用普通完整重推，不能用 C/W 隐藏标签分流。

同样，拒绝了 R 不自动恢复已写入 R 的上下文。可以复用合法的 pre-R 因果尾前缀，但必须恢复适当的 logits、位置、输入历史、RNG/processor/stop 状态；“active prefix 恢复”不等于正确答案保证。若直接从有证书的符号状态输出 z，需声明这是确定性提交，强基线也应享有相同能力。

## 3. 建议保留的主算法骨架

工作名可继续用“版本一致的局部重推”，不先承诺原创性或绑定 KV：

1. **形成可观察的修订候选。** 解析原规则、旧数值断言与新断言，保留来源和版本；不把 Wait 当成修订真值。
2. **G 分级认证。** 输出 accepted / rejected / no-change / unknown，并附依据。精确 AST/算术是受控 oracle；模型似然只能是启发信号，不能与 exact-verification 混为一项。
3. **D 计算版本闭包。** 撤回旧根及完整后代值，保留不变规则和确有证书的独立支持；多个直接子节点形成 ready frontier 集合，不能只固定一个 y 后就跳到汇合 z。
4. **T 有界重推。** 每个候选步明确目标、规则、当前父值/版本和结果。父值未就绪的节点不得推进。格式检查与精确数值检查分开计费、分开命名；若 checker 已经直接计算正确结果，应如实说明模型和工具各自做了什么。
5. **提交/回退。** z 已认证且输出预算足够才提交；否则记录未完成/弃权。所有失败尝试、追问、强制 frame 和最终输出都占同一预算，不把被拒绝分支藏掉。

该骨架的研究价值可以是较少重复计算、较好地使用当前有效状态、减少给定预算下的传播失败。价值不必表现为缓存算法；但应区别于普通状态摘要、工具执行和增量依赖重放的现有思想，靠可复现增量定义贡献。

## 4. 公平的强基线应比附件中的三个更具体

不应把 Generic-OneLine/Self-Ask 固定成“总是傻乎乎从 x/r 开始”的弱实现。新建议提供了认证值和前沿后，至少需要这些比较：

| 方法 | 作用与公平要求 |
|---|---|
| G + 简单路由 | 当前最终值有证书则 Direct；否则用普通重推。与主方法共享同一个 G 和拒绝动作，隔离门控收益 |
| G + Compact-OneLine | 只写一个完全代入的数值表达式，避免反复展开 x/y 与复制长等号链；同样可读取认证状态，控制 64-token 格式瓶颈 |
| G + Self-Ask / 普通步进 | 使用相同工具、规则和认证父值，允许自行省略已知节点；不人为禁止它跳过已认证 x/r |
| 版本工作帧 + ready frontier | 只新增显式版本、dirty 集/调度与节点提交，检查它是否仍有真实增量 |
| Exact AST 全重放参考 | 合成题上合法的精确工具上界/成本参考；若工具已能直接解全题，不能只给主方法工具、让基线裸推理 |

P-only、P+R 是有用能力/干扰控制，但必须实测，不能预设 100%。P+R 的 W 仍含错误修订；它不能直接等价为“已认证 x”。

建议分权限层报告，而非把它们混成一张赢家表：无外部认证层；共享已认证根值/结构的受控层；全精确 AST oracle 层。主方法和基线在同一层比较。若主方法直接拿到正确 y/z、完整 DAG 或旧状态有效标签，那是额外信息/工具能力，必须给对应基线，或明确标为离线上界。

原 16 例和新 12 状态都属于开发材料；后者只是两程序 × 两位置 × E/C/W，不是另外 12 道独立题。当前 r 仅为 `6*4` 或 `13+5` 的短分支，附件所说“尤其长独立 r 的优势”尚无对应数据。

## 5. 尾窗提交可作为共享工程基线，不能叫零成本

预算内 reserve 是实用思路，但不能固定断言“注入占 4 token，答案只需 2 token”。实际冻结上下文里 `最终答案：` 的增量是 3 token；带换行、不同截断位置的拼接仍需用同 tokenizer 冻结。W03 的真实答案 `121` 已需 **3 个数字 token** `[16,17,16]`，加 EOS 共 4；最后两个位置本来就不够它完整提交。

强制插入文本也要更新模型状态、执行前向并占 token/时间。它不是模型自由生成的 token，但仍是解码输入/输出位置与计算，不能计为免费。若第 58 token 时 z 还没算出，插入“最终答案”不会创造正确结果；截断未完成算式还可能损害答案。

可实现的版本是：在声明了答案语法/长度上界的任务上，预留 `实际提交前缀长度 + 答案上界 + 终止开销`；只在 z 已就绪时提交，否则保留未完成状态。自然开放答案没有固定两 token 保证。

第一轮最好给所有比较方法相同的提交策略，先判断工作帧是否有增量；若要研究 reserve 自身，作为独立开关另报。不要把通用输出保护的收益全部归给版本重推。

## 6. 下一轮最小实用设计

### 先完成 CPU 设计冻结

明确输入边界、G 的可用证据、旧状态有效性证书、规则/值版本、frontier 集、unknown 动作，以及统一的预算/提交策略。冻结紧凑基线提示和输出解析器；不根据旧五道失败把正确 y/z 写进专用提示。精确 oracle 与可观察实现分开保存。

### 再选一个权限层、一个预算做短配对

优先比较共享 G 的简单路由、Compact-OneLine、普通步进和工作帧，先固定 64-token 总口径。不要同轮叠乘 64/40/32、原16/新12、KV、probe、reserve 及多套 G。第一固定 E/C/W 块实测完整成本后，按冻结顺序完成可负担的完整配对；预算到了报告部分，不挑短题补齐，也不预言两分钟完成。

初轮主指标应是最终交付正确、解析成功/弃权、C/W 额外损害，以及包括 G、工具、frame prefill、所有重推/追问/强制提交在内的真实请求时间。生成 token 单列，但不替代总成本。先拿真实强基线增量，不急于扩大 probe 或训练。

如果工作帧优于普通宽泛 OneLine，却不优于共享 G 的紧凑基线，研究结论应归为有效的路由/提示设计；不能继续声称必须有更复杂控制器。若在合成结构上有稳定增量，下一阶段才用未参与提示设计的新程序/自然前缀复核。

## 7. P1 规则筛选只做提名，不能替代阴性审查

Wait/“不对”加数值赋值变化可以提高标注效率，但会漏掉隐式修订、符号约束变化、实体别名、无反向词的更正和多分支计划调整。“通常只有 20–35 题”是建议方预测，不是当前已测数量。未被规则提名的另外约 70 条，不能直接标成无修订。

可用两种务实方案：对冻结 100 条全部做一次轻量人工第一遍，把候选送详细审查；或详细审候选，同时对规则阴性层做预先随机抽检、记录抽样概率和漏检，不把未审条目当 0。只标提名子集时，只能报告该子集的事件与误报，不能报告整个 100 条自然发生率。

E-Reuse 和 E-Misbind 可分列，但正确修订、变量身份、规则适用性和传播使用均需单独确认。字符串再次出现不是实际使用的充分条件；没有旧数复现也不自动证明新值跳步。含糊情况保留 unknown。既往数值候选边只是搜索索引，不是已认证的因果依赖图。

## 8. 若效果不好，应保留的解释与下一检查

| 实测结果 | 解释候选 | 下一检查/停止条件 |
|---|---|---|
| 简单路由/紧凑基线与工作帧相当 | 收益主要来自共同 G、输入信息或输出压缩 | 保留较简单方法；停止声称 frontier 独有增益 |
| E 改善但 C/W 新受损 | 旧终值未认证、G 误接受/误拒绝、版本缺边或拒绝分支未隔离 | 同输入检查 G 与状态证书；不以总体均分掩盖伤害 |
| 格式落地但数值仍错 | 语法约束不等于语义 checker，或父值过期 | 分开验证数值和版本，完整计入工具/重试成本 |
| 只在 64-token 截断上占优 | 可能是预算分配/提交策略优势 | 用共享提交基线和同真实成本比较；限定为给定预算收益 |
| 工具层接近全对、无工具层无增益 | oracle/执行器提供了主要能力 | 分权限层报告；不包装为模型推理能力提升 |
| 自然事件少或依赖识别大多 unknown | 受控现象适用面窄/观测不足 | 收缩问题，不扩展训练和大规模生成 |

“50% 省 token”和“90%+”应写成未获支持的预期，后续只报告真实值；不能为了实现这些数字继续改提示、换 seed 或删不利例子。

## 9. 当前Phase索引下的后续子阶段

仓库已按完整研究历史采用Phase1–5，见docs/phases/INDEX_ZH.md。下列是Phase5内部及后续的推进层次，不重新编号既有Phase。借鉴ContractKV的独立总报告、原始证据、问题台账和下一步决定组织方式，不继承其结论或硬件成果。

- **Phase5-A：继承证据与机制边界。** 收入原 P0/P0.5 原始输出、partial 诊断、源/输入/model/parser hash、独立复算、CPU 尾裁剪/中段对照及形式反例。状态明确为“这些工作已完成；100 条语义标注未完成”。
- **Phase5-B：同权限、同预算主算法。** 收入认证/版本/frontier/提交契约、强基线、冻结输入和实施记录；实验与候选设计分区，未执行方案不能放进 achieved results。
- **后续Phase6候选：独立适用面与完整成本。** 使用新问题/新自然前缀、可靠事件标注及工具/端到端成本验证；与Phase5开发集分离。只有这一步有证据后才扩大方法或论文 claim。

仓库可以展示当前清晰的负结果和转向理由，这比预告一个未来高分更可复现。当前最具体的进展是已缩小主问题、知道哪些基线和权限必须公平；下一轮真正需要取得的是相对于这些强基线的实际增量。
